<objective>
Replace `TeletypeApp._run_print_pipeline`'s duplicated ~90-line synchronous pipeline body with a `@work(thread=True)` worker that calls the shared `render_document` from Plan 33-01, passing `cancel_check` wired to the worker's `is_cancelled` flag. This completes PIPE-01 (both consumers on one implementation) and fixes WR-01: `time.sleep` pacing moves off the event loop into the thread, so the existing `escape → action_cancel_stream` binding can actually fire mid-print, and `PrintCancelled` unwinds through the core's `finally: renderer.close()` leaving printer style state clean.

Moving pacing to a thread removes the implicit event-loop mutex that previously serialized all printer writes. This plan therefore also adds an explicit mutual-exclusion guard: while a print worker is unfinished, chat submission / markdown open / typewriter mode refuse with a notify; while ANY other driver writer is unfinished (chat stream worker OR TypewriterScreen's key-processing worker — the app-level ctrl+o binding stays reachable while TypewriterScreen is mounted), `_run_print_pipeline` refuses. This preserves the Phase 31 / MD-08 byte-ordering contract on the physical driver (T-33-07).

Purpose: WR-01 documented that a 5,000-char paced document freezes the whole TUI for 6+ minutes with the advertised cancel path dead. The review's own fix recommendation — thread worker + between-character `is_cancelled` checks — is exactly what the shared core's injectable `cancel_check` was built for.

Output: refactored tui.py adapter with printer mutual exclusion, cancel-path + guard tests, full 932+ suite green.
</objective>
