# v1.6 Architecture Review

## Strengths

- **Layering is fundamentally sound.** Screens and tui.py import only public names from `printing/` submodules; `rendering/` has zero upward imports; the dependency direction (screens → printing → nothing app-level) holds. `python -c "import claude_teletype.printing, .cli, .tui, .diagnose"` loads clean — no import cycles, and the two known cycle risks (profiles↔catalog, detection↔discovery) are broken with documented function-local imports (`profiles.py:325-339`, `detection.py:232-234`).
- **`classify()` is a real seam, used consistently.** The same detection path serves the setup screen (`screens/printer_setup.py:285`), the CLI auto-detect fallback (`detection.py:218` via `cli.py:494`), and diagnose (`diagnose.py:33`). Bridge-first ordering means a CH341 VID can never auto-suggest a printer profile from any of the three entry points — the core hardware-safety invariant is enforced in one function.
- **`SetupDecision` genuinely fixed the sentinel overload.** `cli.py:956-998` sets an explicit decision per path; `tui.py:172-182` gates on the enum, with a documented back-compat shim for direct constructions (`tui.py:160-165`).
- **The frozen-app seam is minimal and one-directional.** `usb_backend.py` is 47 lines; runtime code touches `sys.frozen` in exactly two places (`usb_backend.py:33`, `discovery.py:30`); `packaging/entry.py` is 9 lines that import `cli.app` and nothing imports packaging back. Dev mode is provably untouched (`backend=None` pass-through). This is the right shape — no findings here.
- **Test patch targets are canonical.** Tallying every string `patch(...)` target across tests: all printer-related targets use `claude_teletype.printing.{discovery,selection,detection,drivers}` paths — zero references to pre-split `claude_teletype.printer`/`profiles` or `*_screen` module paths. `selection.py:12` routes calls through `_discovery.` module attributes specifically to keep `discovery.*` patch targets working, and documents it. `KNOWN_MODEL_PIDS` → registry integrity is already asserted (`tests/test_profiles.py:1284-1293`).
- **Catalog provenance discipline.** Every byte in `catalog/epson.py`, `oki.py`, `star.py` carries a manual citation; unverifiable capabilities go to `human_needed` instead of fabricated bytes. This is the data-contract culture the project's core value depends on.

## Findings

### ARCH-01 [warning] — Print pipeline duplicated ~90 lines between cli.py and tui.py

**Evidence:** `cli.py:279-408` (`_render_markdown_to_driver`) and `tui.py:512-618` (`TeletypeApp._run_print_pipeline`) both implement: speed-mode branch → pacer/bell `text_dest` with `time.sleep(base_delay * CHAR_DELAYS[classify_char(char)])` (`cli.py:337-342` vs `tui.py:573-579`) → `WordWrapper` construction → `chunk_writes` style_dest with `buffer_bytes` fallback to 256 (`cli.py:354-363` vs `tui.py:554-587`) → transcript parallel collector (`cli.py:369-375` vs `tui.py:591-593`) → `render` / `wrapper.flush()` / `getattr(driver, "end_response")` / `write_printed_file` epilogue (`cli.py:383-402` vs `tui.py:604-612`).

They have already diverged: the CLI path validates `speed_mode` (`cli.py:288`) and calls `renderer` without a `finally: renderer.close()` (only `driver.close()` at `cli.py:403-406`), while the TUI path has the FLOW-05 `finally: renderer.close()` cancel-safety (`tui.py:616-618`) but no driver close. The next pipeline change (e.g. validating `buffer_bytes` fallbacks on real hardware) must be made twice or the two paths behave differently on the same file.

**Recommendation:** Extract one `render_document(driver, profile, text, *, speed_mode, base_delay_ms, no_audio, transcript_write)` free function (natural home: `rendering/` or a small `printing/pipeline.py`), with both the `renderer.close()` and driver-epilogue semantics decided once. cli and tui become thin adapters (driver acquisition and error surfacing differ; the pipeline should not).

### ARCH-02 [warning] — ProfileRegistry degrades to a dict at every boundary, then gets rebuilt

**Evidence:** `cli.py:843` flattens the registry (`all_profiles = registry.all()`) and threads a plain dict into `TeletypeApp` (`tui.py:131` — typed `all_profiles: dict`), which forwards it to `PrinterSetupScreen`, which **reconstructs a second ProfileRegistry from the dict** (`screens/printer_setup.py:104-106`). Meanwhile `create_driver_for_selection` (`selection.py:100,164-168`) takes the dict, falls back to module-level `BUILTIN_PROFILES` when None, and looks up with `profiles.get(name)` — dict semantics, so an unknown profile name **silently returns None and skips profile wrapping** (unwrapped generic driver), whereas `ProfileRegistry.get` raises with the available-names list (`registry.py:98-102`). Two lookup APIs with different failure semantics coexist: `profiles.get_profile` (`profiles.py:453-468`) and `ProfileRegistry.get` are line-for-line duplicates.

The registry is a real seam for VID:PID matching (`classify` consumes `match_vidpid` through a Protocol, `detection.py:158-161` — good). For name resolution and driver creation it is a pass-through: built in `cli.py:465`, flattened at `cli.py:843`, rebuilt at `printer_setup.py:104`.

**Recommendation:** Pass the `ProfileRegistry` object itself through `TeletypeApp` → `PrinterSetupScreen` → `create_driver_for_selection` (it already exposes `.names()`, `.get()`, `.all()`, `.match_vidpid()` — everything the consumers need). Delete the reconstruction at `printer_setup.py:104` and the `BUILTIN_PROFILES` fallback at `selection.py:113,165`. Decide one failure semantic for unknown names at driver-creation time (log + generic is defensible for saved-config staleness, but make it explicit, not a dict-`.get` accident).

### ARCH-03 [warning] — Adding a printer family touches 3 data homes plus a hand-edited import tuple

**Evidence:** Profile data now lives in three places: (1) the `BUILTIN_PROFILES` literal — juki-6100/2200, escp, ppds, pcl, oki-3390, citizen-cts2000 are still inline (`profiles.py:127-322`, ~200 lines); (2) `catalog/` modules for epson/oki/star merged via `_load_catalog()`, whose module list is a hand-maintained tuple: `from claude_teletype.printing.catalog import epson, oki, star` / `for module in (epson, oki, star)` (`profiles.py:334-337`); (3) eight `dataclasses.replace` alias blocks appended after the merge (`profiles.py:349-450`). Detection hints live in a fourth place (`detection.py:116-130`) with a stringly-typed contract to catalog keys — mitigated by the existing integrity test (`tests/test_profiles.py:1284`).

Concretely, adding the next family requires: new `catalog/<family>.py` + edit the import at `profiles.py:334` + edit the tuple at `profiles.py:337` (+ optionally `detection.py` pins). Two edits in `_load_catalog` per family is the avoidable part; the alias-ordering constraint ("must run AFTER the literal, BEFORE the aliases", `profiles.py:342-345`) is position-dependent module-level execution that a new contributor can silently break by inserting in the wrong place.

**Recommendation:** For v1.7: (a) auto-discover catalog modules with `pkgutil.iter_modules(catalog.__path__)` so a new family is exactly one new file; (b) migrate the remaining inline families from the `BUILTIN_PROFILES` literal into catalog modules (juki.py, citizen.py, ...) so there is one home; (c) move the alias blocks into their family's catalog module (aliases of ppds go where ppds lives), eliminating the ordering constraint. The frozen-dataclass + verbatim-bytes contract stays untouched.

### ARCH-04 [warning] — Smart-startup profile hand-off relies on caller-side mutation of a returned dataclass

**Evidence:** `match_saved_printer` hardcodes `profile_name="generic"` in both returned selections (`selection.py:82,91`) even though the caller has the saved profile in hand. `cli.py:989` then patches it after the fact: `saved_match.profile_name = config.saved_printer_profile or "generic"`. If any future caller of `match_saved_printer` forgets this mutation, the saved printer reconnects with the wrong (generic) profile — no error, just missing ESC init/CRLF behavior on hardware where that matters (the exact class of bug the CH341 atomic-CRLF contract exists to prevent). The double resolution at `cli.py:996-997` (profile looked up again for status-bar display) is a smell from the same conflation: matching "is the device present" and deciding "what profile drives it" are split across two files with a mutable dataclass as the courier.

**Recommendation:** Add a `profile_name: str = "generic"` parameter to `match_saved_printer` and populate the returned `PrinterSelection` there — one call site (`cli.py:982-986`) changes, the mutation at `cli.py:989` deletes. Optionally freeze `PrinterSelection` afterward so this class of hand-off cannot recur (`PrinterSetupScreen._on_connect` constructs it in one shot already, `printer_setup.py:316-323`).

### ARCH-05 [warning] — cli.main() remains a 300-line god function; the --teletype branch is a whole sub-app inline

**Evidence:** `cli.py:734-1040`. `main()` sequentially performs: config merge (823-832), profile resolution (836-843), backend creation with fallback UX (852-883), startup-warning check (886-890), stdin detection (893-894), the complete `--teletype` flow — USB discovery, IOKit fallback listing, CUPS fallback listing, device-file fallback, all with inline Rich formatting (896-947, 51 lines), printer discovery + smart-startup matching (949-998), and both run modes (1000-1040). The refactor cleaned up the print path well (`_resolve_profile_selection` at 419 is genuinely shared, REF-05 delivered), but the teletype branch is untouched: it is the only place in `cli.py` that imports `discover_macos_usb_printers` and `discover_usb_device_verbose`, and it owns presentation logic that belongs beside `teletype.py`.

**Recommendation:** Extract `cli.py:896-947` into a `_run_teletype_mode(config, resolved_profile, console) -> int` (or move the discovery-diagnostics presentation into `teletype.py`, which is only 79 lines). That single cut takes `main()` under 250 lines and removes 3 of its 9 responsibility clusters. Backend-creation-with-fallback (852-883) is the next candidate but is cohesive enough to defer.

### ARCH-06 [info] — tui.py reaches into ProfilePrinterDriver._inner private attribute

**Evidence:** `tui.py:344-345`: `if isinstance(driver, ProfilePrinterDriver): inner = driver._inner` — the status bar unwraps the private inner driver to name the connection type. This is the only screens/tui reach-in past a printing public surface found in the review; everything else goes through exported names.

**Recommendation:** Add a read-only property on `ProfilePrinterDriver` (e.g. `inner` or a `connection_kind: str`) and use it in `_printer_info()`. One line each side.

### ARCH-07 [info] — Stale shim-era docstrings and an unused 91-line package facade

**Evidence:** `printing/__init__.py:5-6` claims "the top-level printer.py / profiles.py shims remain for pre-split absolute-import compatibility" and `screens/__init__.py:4-7` claims "top-level `*_screen.py` modules remain as re-export shims" — both shim sets were deleted (no such files exist under `src/claude_teletype/`; PROJECT.md confirms "shims deleted after migration"). Additionally, the full re-export facade in `printing/__init__.py` (28 names, `__all__`, 91 lines) has **zero consumers**: no source or test file does `from claude_teletype.printing import X` (the only package-level import is `selection.py:12` importing the `discovery` submodule). All 20+ importers use submodule paths directly.

**Recommendation:** Fix both docstrings (5-minute change). Then either declare the facade the public API and use it, or trim it to nothing like `rendering/__init__.py` and `screens/__init__.py` already are — an unused re-export list is a second place to forget when a submodule's surface changes.

### ARCH-08 [info] — Three parallel juki back-compat paths, plus one dead parameter

**Evidence:** Juki backward compatibility exists as (1) the `"juki"` alias profile (`profiles.py:446-450` — sufficient on its own), (2) the deprecated `JukiPrinterDriver` subclass with class-constant byte attributes still exercised by ~6 tests (`drivers.py:400-413`, `tests/test_printer.py:508-590`), (3) the deprecated `juki: bool` parameter on `discover_printer` (`selection.py:176,191-193`) and (4) `config.juki` + `honor_config_juki` plumbing (`config.py:99`, `cli.py:424,488-490`). Separately, `_render_markdown_to_driver`'s `all_profiles: dict` parameter (`cli.py:228`) is **never referenced in the function body** — it is threaded through three call sites (`cli.py:586`, `651`, and via `_make_markdown_picker_app`'s closure) for nothing.

**Recommendation:** The alias profile is the load-bearing compat; (2)-(4) are candidates for a single v1.7 deprecation-removal commit (the tests pinning `JukiPrinterDriver.RESET` bytes should re-pin against `BUILTIN_PROFILES["juki-6100"]`). Delete the dead `all_profiles` parameter now — it is a five-line diff and removes a misleading signature.

### ARCH-09 [info] — CUPS entry population duplicated inside PrinterSetupScreen

**Evidence:** `screens/printer_setup.py:188-201` (`on_mount`) and `415-427` (`_refresh_discovery`) contain the same 12-line CUPS OptionList/entry-building loop, including the identical "No printers found." placeholder block. USB population was correctly extracted to `_add_usb_device_options` (145) during the v1.6 work; the CUPS half was not.

**Recommendation:** Mirror the USB extraction: `_add_cups_options(option_list)` used by both. Cosmetic, but it finishes the pattern the refactor started.

## Candidates for v1.7

Ranked by (risk of divergence × cost of the bug class it prevents):

1. **ARCH-01 — unify the print pipeline.** Already diverged on cancel-safety (`renderer.close()` present in TUI, absent in CLI); every future pacing/buffering fix is a double-edit until this lands. Highest-value single phase.
2. **ARCH-02 + ARCH-04 — make ProfileRegistry the actual currency of the selection flow.** One phase: pass the registry through, delete the dict fallbacks and the caller-side `profile_name` mutation, freeze `PrinterSelection`. Directly hardens the classify → setup → SetupDecision → create_driver hand-off chain this review traced.
3. **ARCH-03 — finish the catalog migration.** Auto-discover catalog modules, move the inline families and alias blocks in. Pays off precisely when "the next 5 printer families" arrive — after this, a family is one file and zero edits elsewhere.
4. **ARCH-05 — extract the teletype branch from main().** Small, isolated, no behavior change.
5. **ARCH-06/07/08/09 — hygiene batch.** Docstring fixes, dead `all_profiles` param, `_inner` property, CUPS-population extraction, juki deprecation removals. Fits as cleanup tasks inside any of the above phases rather than a phase of its own.
